A view is an object with an id, the conditions under which it applies, and
`render`. No framework, no build step of its own, no base class. Everything
on this page is running in your browser through the same library a pod
serves.

```ts
type View = {
  id: string                                  // an IRI
  when?: Condition[]                          // where it applies by default
  render(resource, ctx, hint?): Promise<Rendered>
}
```

## A view that only renders

`render` receives the [`Resource`](/docs/view/contracts/) and returns an HTML
string. Reading RDF needs no library: `objects(quads, subject, predicate)`
scans the array the host handed over.

```ts
import { escapeHtml, objects, type View } from '@aleph-garden/view'

const SCHEMA = 'https://schema.org/'

export const personCardView: View = {
  id: 'https://example.org/views#PersonCard',
  when: [{ type: `${SCHEMA}Person` }],

  async render (resource, ctx) {
    const graph = resource.graph ?? []
    const name = objects(graph, resource.iri, `${SCHEMA}name`)[0]?.value ?? resource.iri
    const employerIri = objects(graph, resource.iri, `${SCHEMA}worksFor`)[0]?.value

    let employer = ''
    if (employerIri) {
      const org = await ctx.resolve(employerIri)
      const orgName = objects(org.graph ?? [], employerIri, `${SCHEMA}name`)[0]?.value ?? employerIri
      employer = `<p class="employer"><a href="${escapeHtml(employerIri)}">${escapeHtml(orgName)}</a></p>`
    }

    return { html: `<article class="person-card"><h2>${escapeHtml(name)}</h2>${employer}</article>` }
  }
}
```

<LiveView iri="https://example.org/people/ada" caption="personCardView over a fixture person" />

Three things in those twenty lines are the whole contract.

**`when` says where the view applies.** A `type` condition holds when the
resource's graph says it has that `rdf:type`. The host consults the
conditions; the view never asks whether it should run. See
[Selection](/docs/view/selection/).

**`ctx.resolve` is the only way out.** The view needs the employer's name,
which lives in another resource, so it asks the host for it. A view never
calls `fetch`, never reads `location`, never touches anything outside the
HTML it returns. The host records what was resolved, so a change to the
employer re-renders this card without the view arranging anything.

**Escaping is the view's job.** Everything that comes out of a resource is
input from elsewhere. `escapeHtml` is exported for that; the runtime also
sanitizes what it writes, and both are wanted.

## A view that behaves

`render` cannot touch the DOM, because it may run where there is none. When
a view needs behaviour it returns `hydrate`, which the host calls after the
HTML is in the document.

```ts
return {
  html: `<div class="checklist"><ul>${items}</ul>
         <p class="tally"><span data-slot="count">${done} of ${tasks.length}</span></p></div>`,

  hydrate (root, ctx) {
    root.addEventListener('click', (event) => {
      const box = event.target as HTMLInputElement | null
      if (!box?.dataset.index) return
      ctx.emit({
        type: ALEPH.Select,
        object: `${resource.iri}#${box.dataset.index}`,
        target: resource.iri
      })
    })

    return {
      update (event) {
        if (event.type !== ALEPH.Select) return
        if (typeof event.object !== 'string' || !event.object.startsWith(resource.iri)) return
        const boxes = [...root.querySelectorAll('.task input')]
        const done = boxes.filter((box) => box.checked).length
        return { slot: 'count', html: `${done} of ${boxes.length}` }
      }
    }
  }
}
```

<LiveView iri="https://example.org/notes/packing.txt" caption="checklistView: tick a box and watch the tally" />

**Events carry meaning.** The view emits `aleph:Select` with the item's IRI,
never a `click`. Other views on the page see that event, and so does the
host, which is how a selection in one region can drive another.

**A handle with `update` takes over its own re-render.** The runtime
re-renders an instance when one of its inputs changes, unless the instance
answers events itself. This one returns a `Patch` naming a `data-slot`, so
the tally is replaced and the checkboxes keep their state. Returning nothing
means the event changed nothing here. See
[Rendering and re-render](/docs/view/rendering/).

## Registering it

A view reaches a page by being in a host's registry. In code:

```ts
import { createRenderer } from '@aleph-garden/view'

const renderer = createRenderer({
  parsers: [],
  views: [personCardView, checklistView, fallbackView]
})
```

Order matters: the first view whose own `when` holds wins, and a view with
an empty `when` holds for everything, which is why a fallback goes last. A
deployment overrides all of it with rules, without touching code. See
[Selection](/docs/view/selection/).

## What a view must not do

- **Fetch.** `ctx.resolve` exists so the host can cache, authorise and track
  what was read.
- **Navigate.** A link in the returned HTML is enough; the runtime turns a
  click into an `as:View` event and the host decides what that means.
- **Write outside its region.** `hydrate` gets the root element of its own
  region. The document around it belongs to the host.
- **Assume a browser in `render`.** Anything needing a DOM goes in
  `hydrate`, which is what lets the same view render on a server.

## Running these examples

Both views live in `packages/view-examples` with the fixture pod they use,
and this page mounts them through the library. Their tests are the same
calls this page makes:

```ts
const resource = await exampleResolve('https://example.org/people/ada')
const { html } = await personCardView.render(resource, ctx)
expect(html).toContain('Analytical Engine Office')
```
