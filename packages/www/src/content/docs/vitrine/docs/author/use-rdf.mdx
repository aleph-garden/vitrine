When a resource carries RDF, a parser the host registered has already turned
it into quads and put them on `resource.graph`. They are plain objects:

```ts
type Term = {
  termType: 'NamedNode' | 'BlankNode' | 'Literal'
  value: string
  datatype?: string
  language?: string
  direction?: 'ltr' | 'rtl'
}

type Quad = { subject: Term; predicate: Term; object: Term; graph?: Term }
```

This is the RDF/JS shape without the prototypes: no methods, no store, no
library. A view that wants a store loads the array into one of its choosing,
and that choice stays inside the view.

## Reading

One helper covers most of what a card-shaped view needs:

```ts
import { schema } from '@aleph-garden/terms'
import { objects } from '@aleph-garden/vitrine'

const name = objects(resource.graph ?? [], resource.iri, schema.name)[0]?.value
```

`objects(quads, subject, predicate)` scans the array and returns the object
terms. `isContainer(resource)` and `typesOf(resource)` are there for the two
questions that come up constantly. Anything more specific is a filter over
the array you already have.

## Naming predicates

A predicate is a full IRI, and writing it out at every call site is how
typos reach production. `@aleph-garden/terms` carries the ones the packages
here share, and `ns` declares any vocabulary it does not:

```ts
import { ns, rdf, schema } from '@aleph-garden/terms'

schema.worksFor          // 'https://schema.org/worksFor'
rdf.type                 // 'http://www.w3.org/1999/02/22-rdf-syntax-ns#type'

const recipe = ns('https://example.org/ns/recipe#', 'Recipe', 'cookTime', 'yield')
recipe.cookTime          // 'https://example.org/ns/recipe#cookTime'
```

Names are listed one by one, so a typo fails to compile and an editor
completes them. What comes out is a plain string, since that is what a
`Term` carries and what every condition compares. A view working in RDF/JS
wraps it in its own `namedNode`, and nothing here has to agree with it about
how terms are represented.

## Selecting

A view that applies to people says so, and the host never has to be told:

```ts
export const personCardView: View = {
  id: 'https://example.org/views#PersonCard',
  when: [{ type: schema.Person }],

  async render (resource) {
    const name = objects(resource.graph ?? [], resource.iri, schema.name)[0]?.value
    return { html: `<article class="person-card"><h2>${escapeHtml(name ?? resource.iri)}</h2></article>` }
  }
}
```

A `type` condition holds when `graph` says the resource has that
`rdf:type`. It never holds when `graph` is absent, which is the case for a
resource nobody parsed.

## What the host says versus what the document says

Two quad arrays arrive, and mixing them up causes bugs that only show on
somebody else's server.

`graph` is the document: what the resource says about itself and about
anything else. `meta` is what the server says about the resource, so
`ldp:contains` for a container, the modification date, the type from a
`Link` header. A listing view reads `meta`; a person card reads `graph`.

`allow` sits beside both, as the modes this requester has. It is a fact
about the request, so it is never in `meta`, where a cached resource would
carry one agent's permissions to another.

## Subjects without an IRI

A blank node has no IRI, so nothing can address it: no rule selects on it,
no link points at it, and transclusion cannot bring it in. It is part of the
resource that carries it, and the view that renders that resource renders it
inline, reached by walking the quads from a subject that does have an IRI.

If you want a part of a document to be addressable, give it a fragment IRI.
`<#claim-1>` is a subject like any other, and a view can hand it to whatever
renders that kind of thing.

## Vocabularies you did not plan for

A resource can carry several vocabularies at once, and no single view owns
such a resource. The parts that have IRIs of their own, including fragment
IRIs like `#claim-1`, are separate resources as far as the library is
concerned, so a view can hand each one to whatever view fits it. That is
what transclusion is for, and it is being built.

Until then, a view that meets a vocabulary it does not know should render
what it does know and leave the rest to the
[fallback](/vitrine/docs/reference/selection/), rather than guess.
