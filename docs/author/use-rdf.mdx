When a resource carries RDF, a parser the host registered has already turned
it into quads and put them on `resource.quads`, next to what the host knows
about the resource from outside. They are plain objects:

```ts
type Term = {
  termType: 'NamedNode' | 'BlankNode' | 'Literal'
  value: string
  datatype?: string
  language?: string
  direction?: 'ltr' | 'rtl'
}

type Quad = { subject: Term; predicate: Term; object: Term; graph?: Term }
```

This is the RDF/JS shape without the prototypes: no methods, no store, no
library. A view that wants a store loads the array into one of its choosing,
and that choice stays inside the view.

## Reading

One reader covers most of what a card-shaped view needs:

```ts
import { schema } from '@aleph-garden/terms'
import { about } from '@aleph-garden/vitrine'

const person = about(resource)
person.one(schema.name)        // "Mara Lind"
person.all(schema.knows)       // every value, from every graph
person.node(schema.worksFor).one(schema.name)
```

`about(resource)` stands on the subject the rendering is about and reads all
of the resource's quads. Inside `render`, `ctx.about()` is the same without
the import. `isContainer(resource)` and `typesOf(resource)` are there for the
two questions that come up constantly, and `objects(quads, subject,
predicate)` scans an array when you have one.

## Naming predicates

A predicate is a full IRI, and writing it out at every call site is how
typos reach production. `@aleph-garden/terms` carries the ones the packages
here share, and `ns` declares any vocabulary it does not:

```ts
import { ns, rdf, schema } from '@aleph-garden/terms'

schema.worksFor          // 'https://schema.org/worksFor'
rdf.type                 // 'http://www.w3.org/1999/02/22-rdf-syntax-ns#type'

const recipe = ns('https://example.org/ns/recipe#', 'Recipe', 'cookTime', 'yield')
recipe.cookTime          // 'https://example.org/ns/recipe#cookTime'
```

Names are listed one by one, so a typo fails to compile and an editor
completes them. What comes out is a plain string, since that is what a
`Term` carries and what every condition compares. A view working in RDF/JS
wraps it in its own `namedNode`, and nothing here has to agree with it about
how terms are represented.

## Selecting

A view that applies to people says so, and the host never has to be told:

```ts
export const personCardView: View = {
  id: 'https://example.org/views#PersonCard',
  when: [{ type: schema.Person }],

  async render (resource) {
    const name = about(resource).one(schema.name)
    return { html: `<article class="person-card"><h2>${escapeHtml(name ?? resource.iri)}</h2></article>` }
  }
}
```

A `type` condition holds when the quads say the subject in focus has that
`rdf:type`, whichever graph says it. For a thing described in RDF the type
does what the content type does for bytes, so the card applies to a person
in Turtle, in JSON-LD, or in the result of a query alike.

## One document, several things

A Turtle file that describes two people is one document and two things. With
no rule for the document itself, it falls to the subjects view: every subject
named `people.ttl#…` is embedded as its own child with `show.fragment`, and
the rules pick the card for each by its type. The view sees the same
`about(resource)` either way, because the fragment moves the subject in focus.

```ts
ctx.transclude('https://pod.example/people.ttl', { fragment: 'mara' })
// drawn by the card, and about(resource).one(schema.name) is "Mara Lind"
```

## What the store says versus what the document says

Every quad carries the graph it came from. What the body says sits in the
graph named by the resource's IRI; what is known about the resource from
outside, its modification date, the type the store gives it, a container's
members, sits in `vitrine:Meta`. Most views never ask, since `about` reads the
union. One that cares narrows the reader:

```ts
about(resource).meta.one(dcterms.modified)   // only from outside
about(resource).content.all(schema.name)     // only what the body says
about(resource).from(otherDocument)          // only one named graph
```

`allow` sits beside the quads, as the modes this requester has. It is a fact
about the request, so it is never among them, where a cached resource would
carry one agent's permissions to another.

## Subjects without an IRI

A blank node has no IRI, so nothing can address it: no rule selects on it,
no link points at it, and transclusion cannot bring it in. It is part of the
resource that carries it, and the view that renders that resource renders it
inline, reached by walking the quads from a subject that does have an IRI. The
subjects view draws the statements about blank nodes as a table beneath the
things it embeds.

If you want a part of a document to be addressable, give it a fragment IRI.
`<#claim-1>` is a subject like any other, and a view can hand it to whatever
renders that kind of thing.

## Vocabularies you did not plan for

A resource can carry several vocabularies at once, and no single view owns
such a resource. The parts that have IRIs of their own, including fragment
IRIs like `#claim-1`, are separate resources as far as the library is
concerned, so a view can hand each one to whatever view fits it. That is
what transclusion is for, and it is being built.

Until then, a view that meets a vocabulary it does not know should render
what it does know and leave the rest to the
[fallback](/vitrine/docs/reference/selection/), rather than guess.
