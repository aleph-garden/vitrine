A wrapper view draws the view that would have drawn the resource without it,
then adds its own markup around that output. It is registered, picked by a
rule or named in a `show`, and replaced like any other view. The one thing it
does that other views do not is call `ctx.render` without a resource.

```ts
type Context = {
  // …
  render(resource?: Resource, show?: Show): Promise<Drawn>
}

type Drawn = Rendered & { view: View }
```

Without a resource, `render` draws the same resource again. Selection runs as
it always does, except that it passes over every view already drawing this
resource with this focus in the current render, so a wrapper never picks
itself or a wrapper around it. The answer is the inner view's output together
with the view that drew it.

A wrapper can name the view it wants inside with `render(undefined, { view })`.
When it names nothing, the rules decide. Fragment and clip carry through to
the inner view unless the wrapper sets them.

Given a resource, `render` draws that one instead of this one. The same view
may draw it again, because a different resource or focus is no cycle. A
wrapper that derives a resource, a graph turned from one shape into another,
hands it on this way and leaves the drawing to whatever the rules pick for it.
Nested calls stop after eight levels, or the depth the host sets, and past it
only a view without conditions is left. [Compose
views](/vitrine/docs/author/compose/) shows both.

What a wrapper draws inside is its own business. The view that embeds the
resource names the wrapper and nothing below it, because a view speaks for
itself and for its direct children only.

## Putting the output inside your own markup

The inner view's `hydrate` has to receive its own root, and a patch it
answers has to land inside the wrapper, where its content now lives. `wrap`
does both:

```ts
import { type View, wrap } from '@aleph-garden/vitrine'

export const outlinedView: View = {
  id: 'https://example.org/views#Outlined',
  async render(resource, ctx) {
    return wrap(await ctx.render(), (body) => `<section class="outlined">${body}</section>`)
  }
}
```

`body` is the inner HTML inside an element `wrap` marks as a slot. The inner
view hydrates on that element, a patch it answers without naming a slot is
written into it, and the wrapper's own markup around it stays untouched. A
third argument to `wrap` is the wrapper's own `hydrate`, which receives the
whole root.

Wrappers nest. With two wrappers and a card registered for the same type, in
that order, the result is `Selector(Inspector(Card))`: each layer calls
`render` and gets the next one down.

## The frame

`frameView` from `@aleph-garden/vitrine/frame` is a wrapper that draws a box
around the inner output and fills up to four corners of it. Each corner is a
function of the resource and of the view that drew the body, so what sits in
a corner can differ from one resource to the next. A corner that is not named
stays empty, and so does one whose function answers `undefined`.

```ts
import { contentType, frameView, name, viewSwitch } from '@aleph-garden/vitrine/frame'

const FILE = 'https://example.org/views#File'

export const fileFrame = frameView(FILE, {
  'top-start': name,
  'top-end': viewSwitch([
    [CHECKLIST, 'Checklist'],
    [PLAIN_TEXT, 'Plain text']
  ]),
  'bottom-start': contentType
})
```

The fields that ship with it are `name`, the last segment of the resource's
IRI with the full IRI as its title; `contentType`, without parameters;
`viewName`, the last segment of the inner view's id; and `viewSwitch`, a menu
over the views you list. A field is any function answering a string, a
`Field` with its own `hydrate`, or nothing.

`frameView` carries no `when`, so it frames only what it is asked to. A view
that transcludes its children decides whether they are framed:

```ts
// each file in a frame, drawn by whatever the rules pick inside it
await ctx.transclude(child, { view: FILE })

// the same file with no frame, exactly as its view draws it
await ctx.transclude(child)
```

A rule that names the frame frames everything it matches instead.

The frame keeps the view it draws inside in its own state, and `viewSwitch`
sets that state. The instance is drawn again, the frame stays, and only its
content changes. The choice holds through every later re-render of the
instance, an `as:Update` on the resource included. It is not announced: no
other instance of the same resource switches with it, and the view inside
never hears about it.

The frame's look comes from the host stylesheet in
`@aleph-garden/host-core`, under the classes `aleph-frame` and
`aleph-corner`.

## Menus

`menu` from `@aleph-garden/vitrine/menu` is the list `viewSwitch` opens, and
it knows nothing about views. It takes a label, a list of entries, and an
optional heading, and answers a field:

```ts
import { menu } from '@aleph-garden/vitrine/menu'

const actions: FieldOf = (resource) =>
  menu('Share', [
    { label: 'Copy address', event: { type: COPY, object: resource.iri } },
    { label: 'Open raw', event: { type: AS.View, object: resource.iri, view: RAW } }
  ])
```

Picking an entry emits that entry's event through the context the menu was
hydrated with, and closes the list. `viewSwitch` hydrates it with a context
whose `emit` takes the pick in and sets the frame's state, which is how a
generic menu ends up switching one frame. The list opens
as a native popover, in the top layer, so a frame or a region that clips its
content cannot cut it off.

## A wrapper that reads the content

A wrapper has the same context as any view, so it can resolve the resource or
anything the resource points at before deciding what to draw around the inner
view. This one counts the words of a note and puts the count above it:

```ts
export const wordCountView: View = {
  id: 'https://example.org/views#WordCount',
  async render(resource, ctx) {
    const words = String(resource.body).split(/\s+/).filter(Boolean).length
    return wrap(
      await ctx.render(),
      (body) => `<p class="word-count">${words} words</p>${body}`
    )
  }
}
```

Every IRI it resolves becomes a dependency of the instance, the same as for
any view, so an `as:Update` on one of them draws the wrapper and its inner
view again.

## State

A view keeps values for its instance with `ctx.state`:

```ts
const count = ctx.state('count', 0)   // a number, 0 until it is set
const view = ctx.state('view')        // a string or undefined
```

`get` answers the current value. `set` stores a new one and draws the
instance again, so a view reads its state while rendering and sets it from a
handler. Setting it while rendering would draw the instance again without end.

The values survive every re-render of the instance: a set, an `as:View`, an
`as:Update`. Mounting the region again, or navigating to another resource,
starts them over. Keys belong to the view that asks, so a wrapper and the
view inside it can both use `'view'` and never meet. Keep values to what JSON
can carry, since a host may one day keep them in the address or in storage.

## How an event reaches an instance

The runtime hands every event to every instance it holds, and each one
decides for itself. An instance whose `hydrate` returned a handle with
`update` answers the event itself, with a patch or with nothing. An instance
without one is drawn again when the event is an `as:Update` on something it
resolved, or an `as:View` on its own resource.
Inside one instance, `wrap` offers an event to the view inside first and to
the wrapper's own handle when the view inside answered no patch, so a view
keeps the events it knows how to answer.
