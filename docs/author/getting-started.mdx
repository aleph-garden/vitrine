A view takes a resource and returns HTML. Here is a whole one, and
it is running further down the page:

```ts
import { escapeHtml, type View } from '@aleph-garden/vitrine'

export const plainTextView: View = {
  id: 'https://example.org/views#PlainText',
  when: [{ contentType: 'text/plain' }],

  async render (resource) {
    const body = typeof resource.body === 'string' ? resource.body : ''
    return { html: `<pre class="plain">${escapeHtml(body)}</pre>` }
  }
}
```

Registered on this page, that view renders a text resource:

<LiveView
  iri="https://example.org/notes/packing.txt"
  view="https://example.org/views#PlainText"
  caption="plainTextView over a text resource"
/>

## Seen from the front

Seen from the front, a view looks like this: `resource.body` and
`resource.contentType` for the bytes, `about(resource)` for the statements.
`resource.quads` is there for views that want the graph as a whole, such as
statements, Turtle and the force diagram.

```ts
import { dcterms, schema } from '@aleph-garden/terms'
import { about, escapeHtml, type View } from '@aleph-garden/vitrine'

export const noteCardView: View = {
  id: 'https://example.org/views#NoteCard',
  when: [{ contentType: 'text/markdown' }],

  async render (resource) {
    const text = typeof resource.body === 'string' ? resource.body : ''  // the bytes
    const title = about(resource).one(schema.name) ?? resource.iri         // the statements
    return { html: `<article><h2>${escapeHtml(title)}</h2><p>${escapeHtml(text.slice(0, 140))}</p></article>` }
  }
}
```

`about(resource)` reads every statement known about the resource, whoever made
it. Three narrower readings are there for a view that cares where a statement
came from:

```ts
// only what is known about it from outside its content: the store, the transport
about(resource).meta.one(dcterms.modified)

// only what its own body says
about(resource).content.one(schema.name)

// only the graphs you name, here metadata a resolver brought in
about(resource).from('https://pod.example/notes/today.md.meta').all(schema.description)
```

## The three parts

**`id` is an IRI**, because a view is a thing that can be referred to: by a
rule, by a link, by someone else's configuration. It never has to resolve to
anything.

**`when` says where it applies.** A `contentType` condition holds when the
resource's media type matches. The host checks it; the view is never asked
whether it should run. Other conditions match an `rdf:type`, a container, a graph, or
an IRI pattern, and [Selection](/vitrine/docs/reference/selection/) has the
list.

**`render` gets the resource and returns HTML as a string.** No DOM, because
a view may run where there is none. Anything that needs elements happens
later, in [`hydrate`](/vitrine/docs/author/interaction/).

## Escaping is yours

`resource.body` came from somewhere else. So does every literal in a graph.
`escapeHtml` is exported for this, and the runtime sanitises what it writes
as a second line of defence. Both are wanted, and the view goes first.

## Getting the package

There is none to get yet. Nothing is on npm, there is no release, and the
`@aleph-garden/vitrine` in the imports above is how the packages refer to
each other inside [the repository](https://github.com/aleph-garden/vitrine).
Clone it, `bun install`, and write your view in a package beside the
examples. It is MIT licensed.

## Registering it

A view reaches a page through a host's registry:

```ts
import { createRenderer } from '@aleph-garden/vitrine'

const renderer = createRenderer({
  parsers: [],
  views: [checklistView, plainTextView]
})
```

Order decides: the first view whose own `when` holds wins. The checklist
view, which [Interaction](/vitrine/docs/author/interaction/) shows, claims
`text/plain` as well and is registered first, so it wins and the plain-text
view above is only reachable by name. The example on this page asks for it by IRI, which is
what `show.view` is:

```ts
await runtime.mount(region, iri, { view: 'https://example.org/views#PlainText' })
```

In a browser host `show` also comes from the URL, as `?view=<iri>`.

## Styling

A view returns class names and no styles. `personCardView` emits
`class="person-card"` with a `.portrait`, a `.lifespan` and an `.employer`
inside it, and what those look like is the host's, the same way the page
around a region is the host's.

That split is deliberate: one view then renders inside a documentation page,
a pod's own chrome and somebody's application without carrying three
stylesheets. It also means a view has to pick class names someone else can
target, and say which ones it emits. A host scopes those rules to the view's
`id`, which the runtime writes on the region as `data-aleph-view`, so a name
has to be unique inside the view's own output and nowhere else. The Markdown view takes this to its
end and emits Obsidian's class names, so a vault's own snippets apply to it
unchanged.

Nothing in the contract enforces any of it. A view that ships a `<style>`
element in its HTML works, and it then owns the consequences in every host
that mounts it.
