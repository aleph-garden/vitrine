A resource is a set of bytes, a content type, and, where the bytes carry RDF, a
set of statements. A view is one way to read that. The same note can arrive as
a checklist, as its own text, as a table of statements, or as a card, and the
resource is the same in every case.

Two views are registered here for `text/plain`, and both of their conditions
hold for this note. The first one registered wins:

Nothing was fetched twice and nothing about the note changed. What differs is
which function drew it.

## Choosing one

`show` names a view directly, as above, and on a browser host `?view=<iri>` on
the address does the same. Without one the host document's rules are tested
in order, and then each registered view's own `when`. `selection.mdx` has the
full order.

A rule is a condition over the content type, the `rdf:type`, the IRI, or
whether the resource is a container. So a deployment says "every recipe looks
like this" in one row, and a reader who wants another reading changes that row
rather than the view.

## A view over a view

A view can draw another view and add something around its output. An
inspector shows a view's output together with the rule that picked it. A
selector takes an inspector and adds a control that changes the choice:

```
Card
Inspector(Card)
Selector(Inspector(Card))
```

Each layer asks for the layer below it with `ctx.inner`, which selects past
every view already drawing the resource, so a wrapper is registered, selected
and replaced like anything else. What a wrapper draws inside is its own
choice, kept in its own state; the view that embedded the resource named the
wrapper and nothing below it. [Wrapper views](/vitrine/docs/author/wrappers/)
has the call, the frame that ships with the library, and a wrapper that reads
the content.

## What a view assumes about its children

A view that meets an address inside its subject hands it back rather than
deciding what is there. `transclusion.mdx` has the call and what the runtime
does with it; what matters here is the boundary it draws. A parent knows its
direct children and nothing below them, so a child can be a kind the parent
has never heard of, served from an origin the parent cannot reach.

The cost is the same property from the other side: a parent cannot ask what
its child became. A view that needed to know would have to branch on the
child's type, and a child that can be branched on can no longer be anything.
