# Ideas, noted while the host slice was built

Raw ideas, each with where it lands in the model. None is decided; a
design picks them up when its slice arrives.

- **The feel of Obsidian, the reach of Notion, the library of Anytype
  (CRDT-backed).** The Markdown view already emits Obsidian's class names
  and the vault's CSS applies. Notion-style blocks and databases are
  Bases and query views (slice 1 deferred). CRDT storage is a pod
  question, outside the view layer.
- **A message from an agent is a resource in the pod.** Claude writes a
  note into an inbox container; RDF on it carries the context (what it is
  about, which session, which resources). The chrome or an inbox view
  shows the link. This is the sticker flow with text instead of an emoji.
- **Backlinks and properties as sidebar views.** Obsidian's "0 backlinks,
  3 properties" strip is a view over the resource's graph and its
  incoming links; a sidebar is a region in a layout. Needs the wikilink
  index turned around (incoming), or a SPARQL host.
- **Right-click on a link: open, open in a view, transclude here.**
  `as:View` already carries a view id; "transclude here" is an `as:View`
  whose target is a region of the current layout. The context menu is the
  chrome's.
- **A dynamic layout view.** A layout resource whose view grows regions
  as links are opened: a tiling or scrolling window manager as a view.
  Each column is itself a region with a layout view, so a column can
  switch between tiling, scrolling, or anything else. Everything
  replaceable through selection. Layout resources are slice 2's deferred
  item; this is what they are for.
- **A user-session daemon as a host without a region.** A systemd user
  unit with client credentials, subscribed to the pod's notification
  channels, turning events into local actions: a Solid notification
  becomes a dbus signal, a hyprctl call, a desktop notification, a
  noctalia message. Anything with addressable content can be driven this
  way. It uses the bus and `resolve` and none of the rendering, so the
  event contract has to stand on its own. The reverse direction holds too:
  a dbus signal becomes a resource in the pod and every other host sees it.
  This is the sidecar from the Quickshell sketch, generalized.
- **Data Cube (qb) with a view per dimension.** A cube view selects on
  `qb:DataSet`, reads the structure definition, and hands each component
  to a sub-view chosen by what the dimension is: a time range becomes an
  axis, a geo dimension a map, a `qb:codeList` a legend or filter, a
  measure a number with its unit. Selection per component is the same
  rule table; this is Fresnel's lens plus formats, declarative where that
  suffices and a code view only where something is drawn. A `qb:Slice` is
  a series and its chart transcludes into the cube view (slice 2). The
  SOSA observations on the pod are one `qb:DataSet` away from the same
  view.
- **Service discovery through the storage description.** LWS Core (an
  editor's draft, April 2025) describes a storage through a resource in
  the shape of a DID document: a `service` array, each entry a `type` and
  a `serviceEndpoint`. Notifications, authentication, the type index and
  search are announced there; the search LWS defines is a
  `TypeSearchService` (filters over types and indexed relations, HTTP
  `QUERY`, `application/lws-query+json`), no full text. The pattern is
  DID Core's and stands on its own. For the shell: the SPARQL endpoint,
  the type index and a full-text search of our own service type belong
  there, each answering RDF, and the host document loses those keys. A
  search view knows the result vocabulary and no backend; Manticore sits
  behind an adapter. `schema:SearchAction` is the website form of the
  same idea and the fallback for hosts without a storage description.
